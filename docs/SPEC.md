# 온사이트 AX 디자인 제너레이터 — 설계 스펙 (Design Spec)

> 작성일 2026-07-10 · 상태: 초안(브레인스토밍 합의 완료, 사용자 검토 대기)
> 한 줄: **기획 내용을 섹션 단위로 입력하면, 새로 정의한 디자인 시스템 기반으로 온사이트 제품소개·매뉴얼 웹페이지를 조립·생성하는 빌드리스 웹앱.**

---

## 1. 목적 · 배경

온사이트 제품소개/매뉴얼 페이지 제작을 효율화한다. 기획 내용을 입력하면 사전 정의된 디자인 시스템·컴포넌트·섹션 패턴으로 웹페이지를 생성하는 제너레이터를 구축·배포한다.

- **MVP(~9월):** 완전 자동 생성이 아니라, 사람이 섹션을 조립하고 슬롯을 채워 페이지를 만든다.
- **고도화(~11월):** AI가 기획 내용을 해석해 적합한 섹션 패턴을 자동 선택·조합한다.
- **운영(~12월):** 섹션·페이지 유형을 확장하고 산출 품질·일관성을 안정화한다.

### 확정된 제품 결정 (브레인스토밍)
| # | 결정 | 내용 |
|---|------|------|
| 1 | 폼 팩터 | **웹 앱** (섹션 라이브러리 + 캔버스 + 슬롯 폼 + 라이브 프리뷰). 비개발자(디자이너/PM)도 사용. |
| 2 | 구성 모델 | **섹션 조립형** — 블록 라이브러리에서 섹션을 골라 순서대로 쌓고 슬롯을 채움. |
| 3 | 디자인 시스템 | **새로 정의** — 온사이트 실서비스 추출이 아닌 이 제너레이터 전용 DS. (산출 룩은 현 온사이트와 별개) |
| 4 | 페이지 범위 | **제품소개 + 매뉴얼 둘 다 9월** (브리프 준수). 공통 섹션 베이스로 중복 완화. |
| 5 | 산출물 | **자가포함 static HTML** (CSS/JS 인라인) → zip 다운로드, 개발 핸드오프. 배포 파이프라인은 MVP 제외. |
| 6 | 아키텍처 | **정적 SPA (빌드리스)** — vanilla JS, CSS 커스텀프로퍼티 토큰. 유저 생태계(빌드툴 없는 static site)와 일치. |

## 2. 비타협 원칙 — 콘텐츠 모델 ↔ 렌더러 분리

파이프라인 전체를 관통하는 단 하나의 절대 규칙.

```
콘텐츠 모델(JSON: PageDoc)  ──┐
                              ├──▶  렌더러(결정론 템플릿)  ──▶  자가포함 HTML
섹션 라이브러리(SectionDef)  ──┘
```

- **MVP:** 사람이 폼으로 `PageDoc`을 채운다.
- **고도화:** AI가 기획을 해석해 **같은 `PageDoc`**을 채운다.
- **렌더러는 두 경우 모두 동일하고 결정론적이다.** LLM은 콘텐츠 모델을 채울 뿐, 마크업을 직접 생성하지 않는다.

이 분리를 처음부터 지키면 고도화 단계에서 재작성 없이 "폼 입력 → AI 출력"만 갈아끼우면 된다. 이것이 MVP를 미래 대비로 만드는 핵심.

---

## 3. 데이터 모델

```jsonc
// PageDoc — 한 페이지의 전체 콘텐츠 상태
{
  "pageType": "product" | "manual",
  "meta": { "title": "", "description": "", "lang": "ko" },
  "sections": [ /* SectionInstance[] — 순서 = 렌더 순서 */ ]
}

// SectionInstance — 캔버스에 놓인 섹션 하나
{
  "type": "hero",          // SectionDef.type 참조
  "variant": "centered",   // SectionDef.variants 중 하나
  "slots": { "heading": "", "subheading": "", "cta": { "label": "", "href": "" } },
  "visible": true
}

// SectionDef — 섹션 라이브러리 정의(코드 자산)
{
  "type": "hero",
  "label": "히어로",
  "pageTypes": ["product", "manual"],   // 어느 페이지타입에 노출
  "variants": ["centered", "split", "minimal"],
  "slotSchema": { /* 슬롯 이름·타입·필수여부·기본값 — 폼 자동생성 근거 */ },
  "template": "(html 함수: variant + slots → HTML 조각)",
  "tokensUsed": ["--surface", "--text", "--brand"]  // DS 충실도 검증용
}
```

**렌더러 계약:** `render(pageDoc, sectionDefs) → string(HTML)`. 순수 함수. 부수효과 없음. 같은 입력 → 같은 출력(안정성 지표의 기반).

## 4. 섹션 분류 (Section Taxonomy)

제품소개(설득·마케팅)와 매뉴얼(절차·참조)은 정보구조가 다르다. **공통 베이스 + 유형별 세트**로 나눠 중복을 줄이고 둘 다 9월 목표를 완화한다.

| 그룹 | 섹션 | 9월 MVP |
|------|------|:---:|
| **공통(4)** | Hero · CTA · FAQ · Footer | ✅ 전부 |
| **제품소개(6)** | Feature(grid/list) · Benefit · Process/HowItWorks · Stats · Testimonial·Logos · Closing | ✅ 핵심 4~5 |
| **매뉴얼(6)** | TOC/목차 · Prerequisite · Manual Step(번호 절차) · Callout(note/warning) · Spec Table · Troubleshooting | ✅ 핵심 4~5 |

- **9월 범위 = 공통 4 + 각 유형 핵심 4~5개.** 나머지 변형·섹션은 10~12월 확장.
- 각 섹션은 1개 이상의 variant를 가진다(예: Feature = grid/list, Hero = centered/split/minimal).

---

## 5. 디자인 시스템 (새로 정의)

빌드리스 = **CSS 커스텀프로퍼티 2계층 토큰**.

```
primitive   색 팔레트 · 폰트 패밀리/사이즈 스케일 · 스페이싱 스케일 · radius · shadow
    ↓ (참조)
semantic    surface / text / brand / border / muted ... + 섹션 role 토큰
```

- 2개 페이지타입을 커버하는 **최소 셋**으로 시작, 섹션이 늘어날 때마다 토큰 누적.
- **라이트 우선.** 다크는 토큰 훅(semantic 레이어)만 남기고 값 정의는 후순위(YAGNI).
- 원칙: 섹션/컴포넌트 CSS에 raw 값 금지 — 전부 semantic 토큰 참조. (DS 충실도 검증 항목)

## 6. 웹앱 UX

3분할 레이아웃:

```
┌───────────────┬──────────────────────────┬─────────────────────────┐
│ 섹션 라이브러리 │  캔버스                   │  슬롯 폼 + 라이브 프리뷰  │
│ (페이지타입    │  (섹션 순서·추가·삭제·이동) │  (선택 섹션의 슬롯 입력   │
│  필터됨)       │                          │   + iframe 실시간 렌더)   │
└───────────────┴──────────────────────────┴─────────────────────────┘
```

**흐름:** 페이지타입 선택 → 라이브러리가 해당 타입 섹션으로 필터 → 섹션 추가/드래그 → 슬롯 채움 → 실시간 프리뷰 확인 → HTML zip 내보내기.

**기본 체크리스트(산출 HTML):** 접근성(대비·키보드·포커스), 반응형, 시맨틱 마크업.

---

## 7. 출력

- **자가포함 static HTML** — CSS/JS 인라인, 외부 의존성 없음.
- **zip 다운로드** → 개발 핸드오프(수정 없이 사용 가능해야 함).
- 원클릭 배포(URL 발급)는 **비목표** (필요 시 운영단계 검토).

---

## 8. 성공 판정 기준 (브리프 공백 보완)

브리프에는 진척률 %만 있고 "무엇이 완료인가" 기준이 없었다. 단계별 통과선을 정의한다.

| 단계 | 통과선 |
|------|--------|
| **MVP (9월)** | 실제 기획 3건 → 제품소개·매뉴얼 각각 생성. **개발이 HTML을 수정 없이 사용 가능**. 실무자 완성도 평가 평균 ≥4/5. |
| **고도화 (11월)** | 기획 텍스트 → AI 섹션 선택이 **사람 선택과 ≥70% 일치**, 명백한 오답 0. |
| **운영 (12월)** | 동일 기획 3회 반복 시 **품질 유지**(안정성). 섹션 10종+ · 페이지타입 안정 운영. |

---

## 9. 단계별 계획 (브리프 진척률 매핑)

| 시기 | 진척률 | 산출물 |
|------|:---:|--------|
| **7월** | 10% | 데이터모델·섹션분류 확정, DS 토큰 v0, 섹션 스키마 문서(AI 구현용 구조 확정) |
| **8월** | 25% | 렌더러 + 섹션 라이브러리(공통4 + 제품소개) HTML/CSS/JS 구현, Claude 테스트 완료 |
| **9월** | 45% | 웹앱(폼 UI + 프리뷰 + export) + 매뉴얼 섹션, 제품소개·매뉴얼 1차 완료 |
| **10월** | 70% | 안정화·산출 품질 보완, 온사이트 적용 결과 검토·개선 |
| **11월** | 90% | 기획 해석 → 섹션 자동 판단(AI) 경로, 내부 검증·피드백 반영 |
| **12월** | 100% | 섹션·패턴 확장, 활용 가이드 정리, 최종 배포 |

**임계 경로:** 8월의 "렌더러 + 콘텐츠 모델 분리"가 심장. 여기가 깨지면 고도화(11월)가 재작성이 된다. 데이터 모델을 처음부터 AI가 채울 형태로 설계할 것.

---

## 10. 비목표 (Non-Goals)

- 백엔드 · 사용자 인증 · DB
- 동작하는 앱 로직(데이터·상태·API) 생성
- 원클릭 배포 / 호스팅 파이프라인 (운영단계 검토)
- 피그마 양방향 동기화
- 온사이트 실서비스 DS 추출·일치 (별개 룩으로 새 DS)

---

## 11. 리스크 · 완화

| 리스크 | 완화 |
|--------|------|
| 제품소개·매뉴얼 둘 다 9월 = 범위 2배 | 공통 섹션 베이스 공유, 각 유형 핵심 4~5개로 9월 범위 축소 |
| 고도화 때 렌더러 재작성 | 콘텐츠 모델↔렌더러 분리를 MVP부터 강제(§2) |
| vanilla JS로 폼 복잡도 한계 | 슬롯 폼을 slotSchema 기반 자동생성으로 단순화, 섹션당 슬롯 수 제한 |
| DS 새로 정의 = 기준점 없어 지연 | 최소 토큰셋으로 시작, 섹션 늘며 누적(빅뱅 금지) |

---

## 12. 미정 (Open Questions)

- 실제 기획서 샘플 확보(MVP 테스트 케이스 3건)
- 완성도 평가자·리뷰 방식(실무자 몇 명, 블라인드 여부)
- 프로젝트 폴더 위치·이름 (사용자가 별도 생성 예정)
- 섹션 라이브러리 최종 개수 확정(9월 핵심셋 선별)
