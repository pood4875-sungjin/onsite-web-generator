# ONSITE Web Generator — PRD

- **작성일**: 2026-07-21
- **상태**: 초안 (설계 합의 v1) — grill-me 검토 대상
- **한 줄**: 기획 내용을 대화로 입력하면, 선택한 스타일 팩으로 웹페이지를 생성·수정·관리하는 AX 웹 제너레이터. (온사이트는 첫 번째 스타일 팩일 뿐, 제너레이터 자체는 스타일 중립)

---

## 1. 최종 모습 (Vision)

여러 **스타일 팩**을 보유한 AX 웹 제너레이터. 사용자가 만들 페이지 종류를 고르고, 내용을 대화로 채우고, 스타일과 모션을 선택하면 최종 HTML이 생성된다. 생성물은 프로젝트로 저장·관리하고, 빌더에서 내용·구조를 수정한다.

- **MVP(9월)**: 페이지 타입 템플릿 기반 + 사람이 대화로 값 입력.
- **고도화(11월)**: 앞단(타입·볼륨·값 매핑)을 AI가 자연어로 추론 + 스타일 팩 확장 + 페이지별 모션.
- **운영(12월)**: 확장·안정화.

핵심 불변식: **앞문(입력 방식)이 바뀌어도 뒷문(PageDoc·렌더러)은 고정.** MVP는 사람이 PageDoc을 채우고, 고도화는 AI가 같은 PageDoc을 채운다. 렌더러는 건드리지 않는다.

## 2. 투 트랙 전략

| 트랙 | 목적 | 방식 |
|------|------|------|
| **A. 제너레이터(기계)** | 제너레이터 개발·테스트 | 온사이트 DS가 아직 없으므로 **샘플 DS 하나**를 팩으로 꽂아 파이프라인을 만들고 검증 |
| **B. 온사이트 자산(콘텐츠)** | 진짜 온사이트 DS 생성 | 온사이트 제품사이트를 실제로 디자인하며 **의도대로 나오는 DS를 협업으로 구축** → 완성되면 트랙 A에 스타일 팩으로 꽂힘 |

두 트랙이 만나는 지점 = **DS 팩 규격**. 트랙 A가 요구하는 팩 규격이 곧 트랙 B가 만들 과녁을 정의한다. 처음부터 샘플 DS로 테스트하므로 제너레이터가 특정 DS에 종속되지 않는다(= 멀티 팩 목표 강제).

## 3. 사용자 플로우 (MVP 파이프라인)

```
① 프로젝트 생성 (종류 선택: 단일/다중)
      ↓
② 페이지 타입 선택 → 템플릿 자동 적용
      ↓
③ 볼륨 선택 (섹션 수: 컴팩트/중간/헤비)
      ↓
④ 콘텐츠 값 입력 (대화창 + 인라인 폼 위젯)
      ↓
⑤ 스타일 팩 선택 (온사이트/모던/엔솔/SK …)
      ↓
⑥ 모션 레벨 선택 (정적/은은/리치)
      ↓
   생성 → HTML
      ↓
   프로젝트에 저장 → 빌더에서 수정
```

- 다중 프로젝트여도 **생성 단위는 항상 페이지 한 장.** 프로젝트는 페이지들을 관리하는 층.
- ⑤ 스타일 팩, ⑥ 모션은 **프로젝트 레벨**(사이트 일관성). ②③④는 페이지 레벨.

## 4. 데이터 모델

```
Project {
  kind          // 단일(랜딩·공지) | 다중(사이트 구축)
  stylePack     // 프로젝트 전역 (H 모델 팩 하나)
  motionLevel   // 프로젝트 전역: static | subtle | rich
  nav           // 다중일 때 공유 네비
  pages[]       // 페이지 목록 (한 장씩 생성/관리)
}

Page {
  pageType      // 이벤트랜딩 | 프로모션랜딩 | 공지 | 제품-메인 | 제품-기능 | 블로그 | 도입문의 …
  volume        // compact | mid | heavy
  pageDoc       // 생성 결과 (섹션 인스턴스 배열)
}

Template {        // 페이지 타입마다 사전 정의 (MVP: 너·나 손저작, 소수 카탈로그)
  pageType
  sections[]      // 순서 + 각 섹션의 볼륨 티어(필수/중간/헤비). MVP=선형만.
                  // 택일(로고 vs 지표 vs 후기)·조건부는 고도화(AI 판단)에서 도입
}

Section {          // 렌더 킷의 원자 (registry)
  type
  slots[]          // 대화가 채우는 값 정의 (타입: text/link/media/list)
  listSlot?        // 반복 항목일 때 min/max (개수는 콘텐츠 주도, 그리드 규칙이 wrap)
  variants[]       // 레이아웃 표현형 (팩이 선택, 사용자 미노출)
}

StylePack {        // 모델 H — 상세는 §6 (8개 범위)
  tokens           // 파운데이션: 색·타이포·간격·라운드·보더/섀도우 (light+dark)
  grid             // 컨테이너·컬럼·거터·패딩 리듬·브레이크포인트
  components        // 버튼·칩·카드·인풋… 팩 스타일
  variantMap       // 섹션 × 페이지타입 → variant 선택
  signature[]      // 간판 섹션 전용 렌더 (2~3개)
  imageryTone      // 일러스트/사진/추상, 미디어 처리 규칙
  motionDefault    // 추천 모션 (사용자가 덮어씀)
}

PageDoc {          // 렌더러 계약 (앞문 무관, 고정)
  sections[]       // [{ type, variant, slotValues }]
}
```

**MVP와 고도화는 앞단이 다르다 (뒷단 PageDoc·렌더러는 동일):**

- **MVP** — 템플릿이 섹션·variant를 이미 확정. 대화는 **빈칸(슬롯) 채우기**만 함. 섹션 선택 고민 없음, 매퍼 없음. → 대화가 곧 PageDoc을 직접 채운다.
- **고도화** — 사용자가 제품을 자유롭게 서술(`원료 ProductBrief`) → **AI 매퍼**가 어떤 섹션 넣을지 설계 + 빈칸까지 채움. → 원료 층과 매퍼는 여기서 등장.

즉 `원료 → 매퍼 → PageDoc`은 **고도화 경로**. MVP는 `대화 → PageDoc(빈칸 채우기)`.

## 5. 아키텍처 원칙

1. **앞문/뒷문 분리** — 입력 UX가 진화해도 PageDoc·렌더러는 고정.
2. **스타일 팩 = 모델 H** — 토큰 DNA + variant 맵 + 간판 전용 렌더. 팩 추가 비용은 "토큰 + variant 선택 + 간판 2~3개".
3. **모션 = 가로지르는 층** — 팩·구조와 독립. 페이지 루트 `data-motion` + 공용 모션 CSS/JS. 팩 안에 넣지 않는다(조합 폭발 방지).
4. **디자인 잠금, 콘텐츠 개방** — 사용자는 내용만 편집, 디자인(토큰·구조)은 팩이 강제. → "아무나 만져도 안 망가지는" 품질 보증.
5. **생성 엔진 = 단일 페이지** — 다중은 반복 + 관리 층.
6. **접근성 기본** — 대비, 키보드, 포커스, `prefers-reduced-motion` 존중(리치여도 격하). 반응형·다크모드 체크.
7. **생성 = 조립(규칙) ≠ 추론(AI).** "생성"에 두 종류. **조립**(정해진 부품+값→규칙대로 배치)은 프로그램 로직, 예측 가능, 무료. **추론**(모델이 판단·창작)만 AI. MVP는 조립만. 레고를 설명서대로 끼우는 것 — 조립에 AI 안 든다.
8. **런타임 디자인 창작 금지.** 팩에 없는 부품을 즉석에서 지어내지 않는다(품질 통제 불가). 없으면 → **팩에 부품 추가(저작 작업)**. 팩 완비도 = 커버리지.
9. **시스템 정의, 낱개 금지.** 값(타이포·간격)을 매번 정하지 않고 **스케일(몇 개) + 섹션이 어느 단계 쓰는지 한 번** 정의 → 무한 페이지가 상속. 이게 DS의 본질이자 "추론 없음"의 실현.
10. **MVP 다양성 = 탑재 자산의 폭.** 지능이 아니라 라이브러리 넓이. 심심하면 → 팩·variant·그래픽키트·아이콘셋을 **더 탑재**(결정론적·무료). 대가 = 사전 저작 노동.

## 6. 스타일 팩 규격 (모델 H) — StylePack Spec

**핵심 원칙 (샌드박스):**
> **팩 = AI의 디자인 어휘이자 한계.** 생성기(사람이든 AI든)는 팩이 정의한 범위 *안에서만* 조합한다. 새 토큰·새 레이아웃을 만들어내지 않는다. → 아웃풋이 항상 일관·온브랜드. AI는 자유 디자이너가 아니라 "정해진 어휘로 조립하는 자".

이 규격은 두 역할을 겸한다: (1) 트랙 B가 온사이트로 만들어야 할 목록, (2) 고도화 때 AI의 디자인 범위(울타리).

### 팩이 정의해야 할 8개 범위

| # | 범위 | 내용 |
|---|------|------|
| 1 | **파운데이션(토큰)** | 색, 타이포, 간격, 라운드, 보더/섀도우, 투명도, elevation |
| 2 | **그리드 & 레이아웃** | 컨테이너 폭, 컬럼/거터, 섹션 상하 패딩 리듬, 브레이크포인트, 정렬 규칙 |
| 3 | **UI 컴포넌트** | 버튼·칩·카드·인풋·뱃지·탭 등 팩 스타일 적용 |
| 4 | **섹션 variant** | 섹션 타입별 레이아웃 안 + `섹션 × 페이지타입`별 어느 variant 쓸지 지정 |
| 5 | **시그니처 섹션** | 간판 섹션(주로 Hero) 팩 전용 렌더 2~3개 |
| 6 | **모션 기본값** | 추천 모션 레벨 (사용자가 덮어씀) |
| 7 | **그래픽 키트** | 팩이 실제로 싣는 자산 세트: 그라디언트·도형/블롭·패턴·배경메시/텍스처·**아이콘셋** + 미디어 처리 규칙(비율·라운드·오버레이). "톤 가이드"가 아니라 *에셋 묶음*. 팩이 밍밍하면 사이트도 밍밍 → 온사이트 팩은 자기 셰이프·그라디언트·아이콘 언어를 가져야 함(트랙 B 산출물) |
| 8 | **다크모드** | light/dark 토큰 셋 둘 다. **기본 라이트**, 생성된 사이트에 **테마 토글** 내장 → 방문자가 전환 (저작자 설정 아님, 출력 기능) |

> **톤&보이스(콘텐츠 문체)는 팩에 포함하지 않는다** — 기획/콘텐츠 영역. 고도화에서 AI 카피 작성 시 원료(기획) 쪽에서 다룸.

**그래픽 소스 (MVP):** ① 사용자 업로드(실제 제품샷·로고 — 제품사이트 최고 소스) + ② 팩 그래픽 키트(추상 요소). 이 둘로 SaaS급 리치한 사이트 나옴, AI 0. AI 그래픽 생성은 후순위(§10 사다리): 안전판 = 팩 색으로 제약된 SVG 벡터 생성 / 커스텀 래스터 이미지는 먼미래·옵션.

**생성형 토큰 지향 (미래 대비):** 토큰을 가능한 한 *고정 값*이 아니라 *규칙·범위*로 설계(예: 액센트 최대 3색, 대비 ≥4.5:1, 배색은 보색/삼각, 채도 60~85%). MVP는 고정 값으로 시작해도, 이 사고로 구조를 잡으면 고도화 때 **AI가 규칙 안에서 새 팔레트 생성**(단조로움 깸)이 자연히 얹힌다.

### 변별력의 원천 (모델 H)

- **토큰 DNA**(1) — 변별력 대부분이 여기서. 색·타이포 성격·간격 밀도·라운드·보더 vs 섀도우.
- **레이아웃 variant**(4) — 팩이 섹션별 레이아웃 지정. 온사이트 Hero=좌우분할, 모던 Hero=센터 대형타이포.
- **시그니처 섹션**(5) — 간판 팩 전용 렌더로 완전 차별화.

트레이드오프: 변별력은 공짜 아님. 팩 하나 = 8개 범위 채우기 + 간판 2~3개 손디자인. 대부분 섹션은 공용 렌더 + 토큰/variant로 갈리고, 간판만 전용.

기존 자산 재사용: `registry.js`(공용 렌더) + `sections.css`(토큰 스킨) + `tokens.css` + `DESIGN_SYSTEM.md`가 이미 이 구조의 기반.

## 7. 모션 시스템

- 3단 다이얼(볼륨과 동일한 UX 패턴): **정적 / 은은 / 리치**.
  - 정적: 애니메이션 없음.
  - 은은: 스크롤 진입 페이드·슬라이드, hover 살짝. (기본값)
  - 리치: 패럴랙스, 카운트업, 스태거 등장, 스티키 스크롤, 캐러셀 자동재생.
- 프로젝트 전역(MVP). 페이지별 오버라이드는 고도화.
- 스타일 팩이 추천 기본값 제공, 사용자가 덮어씀.
- 항상 `prefers-reduced-motion` 존중.

## 8. 편집 단계 (빌더)

생성 후 빌더에서 수정. **디자인 층은 잠금, 콘텐츠·구조 층만 개방.**

| 층 | 편집 가능 |
|----|-----------|
| 콘텐츠 | 텍스트, 링크(href), 미디어 교체(이미지·영상·gif) |
| 구조 | 섹션 순서 재배치, 삭제, 추가(타입별 섹션 팔레트에서) |
| 디자인 | ❌ 잠금 (토큰·레이아웃은 팩이 강제) |

기존 드래그 빌더(`app/builder.html`)가 구조 편집의 기반. 여기에 인라인 콘텐츠 편집을 얹는다.

## 9. 출력 / 패키징

**원칙: PageDoc = 단일 진실원본(SSOT). 출력 포맷마다 독립 익스포터.** 새 포맷 추가 = 익스포터 하나 더, PageDoc·팩 구조는 불변.

### 출력 타깃 3개

| 타깃 | 익스포터 | 시기 | 비고 |
|------|---------|------|------|
| **미리보기 + 개발 핸드오프** | **깔끔 시맨틱 HTML + 토큰 CSS** | MVP | 보기용·개발용 겸용. 매직넘버 없이 CSS 변수. flexbox 기반 → Figma 변환 품질도↑ |
| **Figma 시안 (Tier 1)** | HTML→Figma 변환 (`html.to.design` 등 플러그인) | MVP~고도화 | 납작한 비주얼 레이어. 커스텀 개발 거의 0. 품질은 깔끔HTML이 받침. 레퍼런스·핸드오프용 |
| **Figma 네이티브 DS (Tier 2)** | PageDoc→Figma 컴포넌트·변수·오토레이아웃 (`cc-figma-*`, `figma-generate-*`) | 옵션·후속 | 진짜 편집형 DS 파일. 팩의 Figma 쌍둥이 필요(추가 저작). 큰 작업 |
| **프레임워크 코드 (React 등)** | 프레임워크 익스포터 | 옵션·후속 | 실제 제품 스택 확정 시 |

- **MVP는 깔끔 HTML/CSS 하나로 "보기 + 개발 + (변환)Figma"를 다 커버.** 렌더러가 처음부터 품질 코드를 뽑는 게 전제.

### 패키징 (HTML 출력)

| 프로젝트 종류 | 형태 |
|---------------|------|
| **단일**(랜딩·공지) | 완전 독립 **HTML 1파일** (CSS·JS 인라인). 어디든 배포 |
| **다중**(사이트) | **실개발식 폴더 + zip** |

```
site.zip
 ├ index.html  features.html  notice.html …
 └ assets/
     ├ pack.css     (= 스타일 팩 토큰, 공통)
     ├ motion.js    (= 모션 층, 공통)
     └ img/*
```

- 다중 페이지는 공통 `pack.css`·`motion.js`·네비를 공유하고 서로 `<a href>`로 연결(실제 사이트처럼).
- 스타일 팩이 프로젝트 레벨이라 공통 CSS 한 파일로 뽑기 자연스러움.

### AI 개입 사다리 (한정성 vs 통제·비용)

한 번에 "고정 팩 → AI가 다 그림"으로 뛰지 않는다. 아래로 갈수록 자유↑ / 통제·비용·리스크↑.

| Lv | AI가 하는 일 | 한정성 깸 | 리스크 | 비용 | 시기 |
|----|------------|---------|-------|------|------|
| **0** | 없음. 팩 고정, 조립만 | — | 없음 | 0 | MVP |
| **1** | 섹션 선택·카피·variant 선택 (값은 팩 스케일 내) | 조합 다양성↑ | 낮음 | 소액(텍스트) | 고도화 |
| **2** ⭐ | **새 토큰셋(팔레트·타이포·리듬) 생성** — 규칙 안에서. 구조는 재사용 | **크게 깸** | 중(대비·조화 검증규칙) | 소액 | 고도화+ |
| **3** | 새 레이아웃/구조를 코드로 생성 | 최대 | 큼(깨짐·품질통제) | 큼 | 프론티어·옵션 |
| **4** | 그래픽 생성 (SVG 벡터 = 안전판 / 래스터 이미지 = 프론티어) | 비주얼 자유 | 큼 | 큼 | 옵션·먼미래 |

핵심: 단조로움 깨는 가성비 지점 = **AI가 "새 레이아웃"이 아니라 "새 토큰 팩"을 생성(Lv2)**. 구조 재사용=품질 보증, 토큰 다양=비주얼 다양. 레이아웃 창작(Lv3)·래스터 생성(Lv4)은 최상위 툴도 조심하는 리스크 프론티어. MVP를 구조·토큰·콘텐츠로 깨끗이 분리하면 이 사다리가 자연히 얹힌다.

### 비용 모델

| 단계 | 무엇 | AI? | 운영비 |
|------|------|-----|--------|
| 레이아웃·스타일 | 팩 완비, 조립만 | ❌ | 0 |
| 콘텐츠 배치(MVP) | 대본 대화(정해진 질문) | ❌ | 0 |
| 그래픽(MVP) | 업로드 + 팩 키트 | ❌ | 0 |
| 정적 호스팅·저장 | 무료티어 + localStorage | ❌ | 0 |
| 섹션추론·카피(고도화) | 텍스트 LLM(싼 모델) | ✅ | 페이지당 소액, 예산 상한·캐싱으로 통제 |
| 토큰 생성(Lv2) | 텍스트 LLM | ✅ | 소액 |
| 이미지 생성(Lv4) | 이미지 모델 | ✅ | 큼·후순위 |

**MVP 운영비 사실상 0.** AI 비용은 고도화의 *텍스트*에만(소액·통제 가능), *이미지 생성*은 완전 별개·먼미래. "다 정리돼 있으면 진짜 무료" — 대가는 돈이 아니라 **사전 저작 노동**.

## 11. 앱 아키텍처 · 배포 · 저장

목표: **최종 전사 사용**, MVP는 **몇몇 구성원**. 제약: **개발 리소스 못 쓸 확률 큼** → 무백엔드 정적으로 간다(앱 자체는 지금 우리가 만드는 정적 SPA라 개발팀 불필요).

| 항목 | MVP | 전사 확장(후속) |
|------|-----|----------------|
| **앱 형태** | 정적 SPA (빌드리스, 브라우저서 조립) | 동일 + 얇은 서버리스 |
| **배포** | **Vercel** 무료티어 → 공유 URL 하나. 몇몇이 링크로 접속 | 동일. 서버리스 함수(AI·인증) 얹기 |
| **저장** | **localStorage(자동) + JSON 내보내기/불러오기** | BaaS(Supabase 등) 클라우드 저장 |
| **공유** | **파일(JSON) 주고받기** (내보내기→슬랙/드라이브→불러오기) | 같은 URL서 실시간 공유(BaaS) |
| **AI** | 없음 | 서버리스 함수로 Claude API(키 숨김) |
| **인증** | 없음 | 필요 시 추가 |

- MVP는 백엔드·계정·DB 0. 운영비 0(§10 비용 모델).
- 실시간 공유·AI·클라우드 저장을 원하는 순간에만 *관리형 서비스*(BaaS·서버리스) 살짝 붙임 — 풀 개발팀 아님.

## 12. 열린 질문 (다음 라운드에서 결정)

6. **다중 프로젝트 네비** — 공유 네비 자동 생성 규칙(페이지 목록 → 메뉴).
