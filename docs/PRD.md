## 0. 현재 상태 스냅샷 (2026-07-23)

> **핵심: 예상보다 빠르게 MVP 엔진에 도달.** "제너레이터 먼저, 팩 나중" 전략이 적중 — 플로우를 실제로 만들며 *어떤 정보를 받아 어떻게 보여줄지*가 확정됐고, 그 결과 빈칸 채우기식 제너레이터는 **완료** 상태. 이제 템플릿·섹션·팩이라는 *재료*만 채우면 MVP 완성.

**완료 (엔진 = 앞문/뒷문 파이프라인)**
- 프로젝트 생성 플로우: 종류(단/다) · 스타일 팩 · 공유 사실
- 대본형 대화 입력: 페이지 타입 → 볼륨 → 섹션별 값 (슬롯 위젯)
- 실시간 섹션 프리뷰 (입력 즉시 렌더 = AX 느낌)
- 빌더/편집: 인라인 텍스트·이미지 교체, 섹션 순서/숨김, 이미지 슬롯
- 다중 페이지 IA: 레일 트리(부모/자식·드래그) → 네비 자동 생성 → 생성 페이지 GNB에 메뉴·링크 반영
- 프로젝트 관리: 대시보드(현황·최근), 목록(필터·검색·다중선택·삭제), 인라인 이름 수정
- 템플릿 갤러리(리소스→템플릿): 미리보기 모달 → 바로 생성·편집 진입
- 출력/미리보기: 새 창 미리보기(다중=SPA), HTML·JSON 내보내기
- 앱 셸 DS(`ds.css`): 라이트/다크, 포인트 보라, 디자인 모달, 공용 SNB/GNB
- **팩 3종(darkglow=개발 비계 · KRDS · MIDAS AX)** — 렌더 계약 검증용. 아직 "진짜 팩"은 아님(비계)

**남음 (MVP 완성)**
- 페이지 타입 카탈로그 + 템플릿(섹션 리스트+티어) 정식화 — §13
- 섹션 빈 곳 채우기(매뉴얼 toc·업데이트노트 changelog·요금 상세 등)
- **온사이트 팩**(실측 DS 추출) — 트랙 B, §2
- 섹션 slotSchema 정식화 — §14

**새 방향 (일부 고도화를 MVP 뒤에 앞당김)** — §3-bis, §13-bis
- NL 프론트도어: 프로젝트 생성 시 자연어 입력 + 파일 첨부 → AI가 단/다·IA·섹션 초기 판단
- 섹션 variant 랜덤 조립: 페이지 타입별 섹션마다 2~3개 표현형 → 결정론적 랜덤으로 다양성(디자인은 여전히 고정)
- 디자인 팩 다수를 **AI로 저작-타임 생성**(런타임 아님) — 10월까지 ≥3팩

## 0.5. 대상 · 우리 역할 · 배포 모델 (2026-07-23)

### 대상 사용자
- **1차: 기획자 · 사업 담당자.** 개발/디자인 리소스 없이 온브랜드 사이트를 뽑아야 하는 사람. → 디자인 잠금·콘텐츠 개방 원칙(§8)이 이들에게 정확히 맞음.

### 우리(플랫폼 팀) 역할
- **디자인 팩 관리 + AX 디자인 플랫폼 고도화.** 우리는 사이트를 대신 만들지 않는다 — *팩과 플랫폼*을 관리하고, 기획자·사업 담당자가 셀프로 뽑게 한다.

### 배포 모델 (확장 방향)
- **단일 URL(MVP)** → **법인/조직 멀티테넌트(후속).** 각 법인이 플랫폼으로 만든 산출물을 **자기 서버/호스팅에 올려** 마케팅(MBM)·사이트 구축에 활용.
- 국내/해외 사업뿐 아니라 **법인 단위 셀프서비스**가 확장 축. 산출물이 자기완결 HTML(단일=1파일, 다중=폴더+zip, §9)이라 어디든 배포 가능 → 멀티테넌트와 자연스럽게 맞물림.

### 준비돼야 할 거버넌스 (후속, 전사·법인 확장 시)
| 항목 | MVP | 확장(법인·전사) |
|------|-----|----------------|
| **권한/역할** | 없음(단일 URL) | 조직·프로젝트별 역할(뷰어/편집/관리), 팩 접근 범위, 승인 흐름 |
| **토큰 사용(미터링)** | 사실상 0 | 조직별 예산 상한·사용량 계량·과금 경계(§10 비용) |
| **테넌시** | localStorage/파일 | 조직 분리 저장(BaaS), 산출물 자기 호스팅 |
| **인증** | 없음 | SSO/조직 계정 (필요 시) |

> 이 거버넌스는 **후속**이다. MVP는 백엔드·계정·권한 0으로 가되(§11), 위 항목이 얹힐 자리를 지금 구조에서 비워 둔다(프로젝트=테넌트 경계 후보, AI 콜=미터링 지점).

### 로컬라이징 (다국어) — 지금 착수 가능
- **출력·앱 양쪽 다국어.** 1차 언어: **한국어 · 영어 · 일본어 · 중국어.**
- **생성 산출물 다국어**(핵심): 해외 사업·법인 대응. 같은 PageDoc에 언어별 슬롯값 → 언어 전환. 레이아웃·팩은 공유(RTL 없음, CJK+라틴 폰트만 고려).
- **앱 UI 다국어**(부차): 기획자·해외 법인용. 문자열 리소스 분리(i18n 키).
- 리스크 낮음·구조 영향 적음 → **근시일 착수 가능**(대본 문구·UI 라벨 i18n 키화부터).

## 1. 최종 모습 (Vision)

여러 **스타일 팩**을 보유한 AX 웹 제너레이터. 사용자가 만들 페이지 종류를 고르고, 내용을 대화로 채우고, 스타일과 모션을 선택하면 최종 HTML이 생성된다. 생성물은 프로젝트로 저장·관리하고, 빌더에서 내용·구조를 수정한다.

- **MVP(9월)**: 페이지 타입 템플릿 기반 + 사람이 대화로 값 입력.
- **고도화(11월)**: 앞단(타입·볼륨·값 매핑)을 AI가 자연어로 추론 + 스타일 팩 확장 + 페이지별 모션.
- **운영(12월)**: 확장·안정화.

핵심 불변식: **앞문(입력 방식)이 바뀌어도 뒷문(PageDoc·렌더러)은 고정.** MVP는 사람이 PageDoc을 채우고, 고도화는 AI가 같은 PageDoc을 채운다. 렌더러는 건드리지 않는다.

## 2. 투 트랙 전략

| 트랙 | 목적 | 방식 |
|------|------|------|
| **A. 제너레이터(기계)** | 제너레이터 개발·테스트 | 온사이트 팩 추출 전에도 개발 막히지 않게 **더미/샘플 팩을 "개발 비계(scaffolding)"로만** 사용. DS 추출되면 온사이트 팩으로 교체 |
| **B. 온사이트 자산(콘텐츠·팩)** | 진짜 온사이트 팩 생성 | **1차: 메인 + 도입문의 페이지 손디자인 → DS 1차 추출 = 온사이트 팩 씨앗.** 이후 나머지 페이지 생성에 사용 |

**MVP 팩 = 온사이트 팩** (메인+도입문의에서 추출). 별도 샘플 DS를 최종 산출로 만들지 않음 — 샘플은 개발 비계용.
**샘플 DS = 탐침(probe):** 제너레이터를 샘플 팩에 물려 *무엇이 없으면 깨지나*를 발견 → StylePack Spec(§6)의 **실제 최소 요건**을 도출 → 트랙 B가 온사이트 팩으로 채워야 할 목록을 역으로 확정. (계획 초기 실험)
**MVP에서 두 트랙이 합쳐진다:** 제너레이터가 *진짜 온사이트 사이트를 실제로 뽑아내며* 자기를 증명. 두 트랙의 이음새 = **DS 팩 규격(§6)** — 트랙 A 요구가 곧 트랙 B 과녁, 팩 교체 가능해 특정 DS 비종속(멀티 팩 목표) 강제.

## 3. 사용자 플로우 (MVP 파이프라인)

```
[프로젝트 레벨 — 한 번]
 ① 종류 선택 (단일/다중)
 ② 스타일 팩 + 모션 선택 (전역, 사이트 일관성)   ← 콘텐츠 前: 프리뷰가 실제 스타일로 나오게
 ③ 공유 사실 입력 (제품명·로고·주CTA·문의링크 …)
      ↓
[페이지마다 반복 — 생성 단위 = 페이지 한 장]
 ④ 페이지 타입 선택 → 템플릿 자동 적용
 ⑤ 볼륨 선택 (섹션 수: 컴팩트/중간/헤비)
 ⑥ 섹션별 값 입력 (대화형 폼 + 섹션 미니 프리뷰)
      ↓ 생성
      ↓
[프로젝트]
   저장 · 관리(페이지 목록) · 빌더에서 수정 · 내보내기(HTML / Figma)
```

- **생성 단위는 항상 페이지 한 장.** 단일 프로젝트면 반복이 1회. 다중이면 페이지마다 ④~⑥.
- ①②③ = 프로젝트 레벨(모든 페이지 공유). ④⑤⑥ = 페이지 레벨.
- 스타일 팩은 입력 중 언제든 교체 → 프리뷰 즉시 리스킨(§12).

## 3-bis. NL 프론트도어 + 섹션 variant (2026-07-23 방향)

기존 대본형 대화(§12)는 그대로 유지하되, **그 앞에 자연어 진입 한 겹**을 얹는다. AI는 *디자인*이 아니라 *구조 판단*에만 개입 — 사다리 Lv1(§10)을 MVP 직후로 앞당김.

### 진입 흐름 (개정)
```
[프로젝트 생성]
 ⓪ 자연어 입력 + (선택)파일 첨부   ← 새 프론트도어
      "사내 협업 캘린더 제품 소개 사이트. 기능·요금·문의 페이지 필요"
      + 기획서/브리프 파일 드롭
      ↓ AI 초기 판단 (1콜, 싼 모델, 카탈로그 캐싱)
      · 단일 vs 다중
      · IA (필요한 페이지들 + 순서)
      · 페이지별 섹션 후보 (카탈로그 안에서만 선택)
      ↓ 초기 셋팅 자동 구성 (레일·페이지·섹션 스캐폴드)
 [좌측 대화 패널]  정보 부족하면 여기서 되물음/추가 입력  ← 기존 대본 대화가 이 자리
      ↓
 (이하 기존 §3 파이프라인: 값 채우기 → 프리뷰 → 빌더)
```

- **AI 판단 범위 = 카탈로그 안에서의 선택**(§13). 새 페이지타입·새 섹션을 창작하지 않음 → 통제·품질 보증 유지.
- 자연어가 부족하면 좌측 대화 패널이 대본형으로 이어받아 채운다 → **NL(있으면) + 대본(항상)** 하이브리드. NL은 편의층, 대본은 안전판.
- 판단 결과는 편집 가능(사용자가 페이지·섹션 조정) → AI는 초안, 결정은 사람.

### 섹션 variant 랜덤 조립 (디자인 고정, 다양성 확보)
- 페이지 타입별 각 섹션에 **표현형(variant) 2~3개**를 팩이 사전 저작 → 조립 시 **결정론적 랜덤/규칙**으로 선택.
- **디자인 자유도는 여전히 0** (AI가 디자인 안 함). 다양성은 *지능*이 아니라 *탑재 자산의 폭*에서 나온다(§5 원칙10). variant는 팩이 만든 부품 = 무료·온브랜드.
- 같은 페이지 타입이라도 매번 조금씩 다른 조합 → 단조로움 완화, 비용 0.

### 디자인 팩 = AI로 저작-타임 생성 (런타임 아님)
- 팩을 사람이 전부 손저작하는 대신, **AI를 저작 도구로** 써서 팩(토큰·variant·그래픽키트)을 다수 생성.
- 중요: 이는 **개발/저작 시점** 비용 — *사용자 런타임엔 AI 0*. 런타임은 완성된 팩을 긁어와 조립할 뿐(디자인에 AI 미적용, 자유도 미부여 — 처음 방침).
- 목표: **10월까지 ≥3팩**(§10 로드맵).

## 4. 데이터 모델

```
Project {
  kind          // 단일(랜딩·공지) | 다중(사이트 구축)
  stylePack     // 프로젝트 전역 (H 모델 팩 하나)
  motionLevel   // 프로젝트 전역: static | subtle | rich
  nav           // 다중일 때 공유 네비. pages[]에서 자동 생성(라벨=페이지제목, 순서=페이지순서), 편집 가능(이름·숨김·순서·외부링크), 홈=메인
  sharedFacts   // 한 번 입력 → 모든 페이지·섹션 자동 주입 (제품명·로고·태그라인·주CTA·문의링크 …)
  pages[]       // 페이지 목록 (한 장씩 생성/관리)
}

Page {
  pageType      // 메인홈 | 도입문의 | 제품기능소개 | 이벤트/뉴스룸 | 업데이트노트 | 매뉴얼 | 요금비교 | 랜딩 (§13 카탈로그)
  volume        // compact | mid | heavy
  pageDoc       // 생성 결과 (섹션 인스턴스 배열)
}

Template {        // 페이지 타입마다 사전 정의 (MVP: 너·나 손저작, 소수 카탈로그)
  pageType
  sections[]      // 순서 + 각 섹션의 볼륨 티어(필수/중간/헤비). MVP=선형만.
                  // 택일(로고 vs 지표 vs 후기)·조건부는 고도화(AI 판단)에서 도입
}

Section {          // 렌더 킷의 원자 (registry)
  type
  slots[]          // 대화가 채우는 값 정의 (타입: text/link/media/list)
  listSlot?        // 반복 항목일 때 min/max (개수는 콘텐츠 주도, 그리드 규칙이 wrap)
  variants[]       // 레이아웃 표현형 (팩이 선택, 사용자 미노출)
}

StylePack {        // 모델 H — 상세는 §6 (8개 범위)
  tokens           // 파운데이션: 색·타이포·간격·라운드·보더/섀도우 (light+dark)
  grid             // 컨테이너·컬럼·거터·패딩 리듬·브레이크포인트
  components        // 버튼·칩·카드·인풋… 팩 스타일
  variantMap       // 섹션 × 페이지타입 → variant 선택
  signature[]      // 간판 섹션 전용 렌더 (2~3개)
  imageryTone      // 일러스트/사진/추상, 미디어 처리 규칙
  motionDefault    // 추천 모션 (사용자가 덮어씀)
}

PageDoc {          // 렌더러 계약 (앞문 무관, 고정)
  sections[]       // [{ type, variant, slotValues }]
}
```

**MVP와 고도화는 앞단이 다르다 (뒷단 PageDoc·렌더러는 동일):**

- **MVP** — 템플릿이 섹션·variant를 이미 확정. 대화는 **빈칸(슬롯) 채우기**만 함. 섹션 선택 고민 없음, 매퍼 없음. → 대화가 곧 PageDoc을 직접 채운다.
- **고도화** — 사용자가 제품을 자유롭게 서술(`원료 ProductBrief`) → **AI 매퍼**가 어떤 섹션 넣을지 설계 + 빈칸까지 채움. → 원료 층과 매퍼는 여기서 등장.

즉 `원료 → 매퍼 → PageDoc`은 **고도화 경로**. MVP는 `대화 → PageDoc(빈칸 채우기)`.

## 5. 아키텍처 원칙

1. **앞문/뒷문 분리** — 입력 UX가 진화해도 PageDoc·렌더러는 고정.
2. **스타일 팩 = 모델 H** — 토큰 DNA + variant 맵 + 간판 전용 렌더. 팩 추가 비용은 "토큰 + variant 선택 + 간판 2~3개".
3. **모션 = 가로지르는 층** — 팩·구조와 독립. 페이지 루트 `data-motion` + 공용 모션 CSS/JS. 팩 안에 넣지 않는다(조합 폭발 방지).
4. **디자인 잠금, 콘텐츠 개방** — 사용자는 내용만 편집, 디자인(토큰·구조)은 팩이 강제. → "아무나 만져도 안 망가지는" 품질 보증.
5. **생성 엔진 = 단일 페이지** — 다중은 반복 + 관리 층.
6. **접근성 기본** — 대비, 키보드, 포커스, `prefers-reduced-motion` 존중(리치여도 격하). 반응형·다크모드 체크.
7. **생성 = 조립(규칙) ≠ 추론(AI).** "생성"에 두 종류. **조립**(정해진 부품+값→규칙대로 배치)은 프로그램 로직, 예측 가능, 무료. **추론**(모델이 판단·창작)만 AI. MVP는 조립만. 레고를 설명서대로 끼우는 것 — 조립에 AI 안 든다.
8. **런타임 디자인 창작 금지.** 팩에 없는 부품을 즉석에서 지어내지 않는다(품질 통제 불가). 없으면 → **팩에 부품 추가(저작 작업)**. 팩 완비도 = 커버리지.
9. **시스템 정의, 낱개 금지.** 값(타이포·간격)을 매번 정하지 않고 **스케일(몇 개) + 섹션이 어느 단계 쓰는지 한 번** 정의 → 무한 페이지가 상속. 이게 DS의 본질이자 "추론 없음"의 실현.
10. **MVP 다양성 = 탑재 자산의 폭.** 지능이 아니라 라이브러리 넓이. 심심하면 → 팩·variant·그래픽키트·아이콘셋을 **더 탑재**(결정론적·무료). 대가 = 사전 저작 노동.

## 6. 스타일 팩 규격 (모델 H) — StylePack Spec

**핵심 원칙 (샌드박스):**
> **팩 = AI의 디자인 어휘이자 한계.** 생성기(사람이든 AI든)는 팩이 정의한 범위 *안에서만* 조합한다. 새 토큰·새 레이아웃을 만들어내지 않는다. → 아웃풋이 항상 일관·온브랜드. AI는 자유 디자이너가 아니라 "정해진 어휘로 조립하는 자".

이 규격은 두 역할을 겸한다: (1) 트랙 B가 온사이트로 만들어야 할 목록, (2) 고도화 때 AI의 디자인 범위(울타리).

### 팩이 정의해야 할 8개 범위

| # | 범위 | 내용 |
|---|------|------|
| 1 | **파운데이션(토큰)** | 색, 타이포, 간격, 라운드, 보더/섀도우, 투명도, elevation |
| 2 | **그리드 & 레이아웃** | 컨테이너 폭, 컬럼/거터, 섹션 상하 패딩 리듬, 브레이크포인트, 정렬 규칙 |
| 3 | **UI 컴포넌트** | 버튼·칩·카드·인풋·뱃지·탭 등 팩 스타일 적용 |
| 4 | **섹션 variant** | 섹션 타입별 레이아웃 안 + `섹션 × 페이지타입`별 어느 variant 쓸지 지정 |
| 5 | **시그니처 섹션** | 간판 섹션(주로 Hero) 팩 전용 렌더 2~3개 |
| 6 | **모션 기본값** | 추천 모션 레벨 (사용자가 덮어씀) |
| 7 | **그래픽 키트** | 팩이 실제로 싣는 자산 세트: 그라디언트·도형/블롭·패턴·배경메시/텍스처·**아이콘셋** + 미디어 처리 규칙(비율·라운드·오버레이). "톤 가이드"가 아니라 *에셋 묶음*. 팩이 밍밍하면 사이트도 밍밍 → 온사이트 팩은 자기 셰이프·그라디언트·아이콘 언어를 가져야 함(트랙 B 산출물) |
| 8 | **다크모드** | light/dark 토큰 셋 둘 다. **기본 라이트**, 생성된 사이트에 **테마 토글** 내장 → 방문자가 전환 (저작자 설정 아님, 출력 기능) |

> **톤&보이스(콘텐츠 문체)는 팩에 포함하지 않는다** — 기획/콘텐츠 영역. 고도화에서 AI 카피 작성 시 원료(기획) 쪽에서 다룸.

**그래픽 소스 (MVP):** ① 사용자 업로드(실제 제품샷·로고 — 제품사이트 최고 소스) + ② 팩 그래픽 키트(추상 요소). 이 둘로 SaaS급 리치한 사이트 나옴, AI 0. AI 그래픽 생성은 후순위(§10 사다리): 안전판 = 팩 색으로 제약된 SVG 벡터 생성 / 커스텀 래스터 이미지는 먼미래·옵션.

**생성형 토큰 지향 (미래 대비):** 토큰을 가능한 한 *고정 값*이 아니라 *규칙·범위*로 설계(예: 액센트 최대 3색, 대비 ≥4.5:1, 배색은 보색/삼각, 채도 60~85%). MVP는 고정 값으로 시작해도, 이 사고로 구조를 잡으면 고도화 때 **AI가 규칙 안에서 새 팔레트 생성**(단조로움 깸)이 자연히 얹힌다.

### 변별력의 원천 (모델 H)

- **토큰 DNA**(1) — 변별력 대부분이 여기서. 색·타이포 성격·간격 밀도·라운드·보더 vs 섀도우.
- **레이아웃 variant**(4) — 팩이 섹션별 레이아웃 지정. 온사이트 Hero=좌우분할, 모던 Hero=센터 대형타이포.
- **시그니처 섹션**(5) — 간판 팩 전용 렌더로 완전 차별화.

트레이드오프: 변별력은 공짜 아님. 팩 하나 = 8개 범위 채우기 + 간판 2~3개 손디자인. 대부분 섹션은 공용 렌더 + 토큰/variant로 갈리고, 간판만 전용.

기존 자산 재사용: `registry.js`(공용 렌더) + `sections.css`(토큰 스킨) + `tokens.css` + `DESIGN_SYSTEM.md`가 이미 이 구조의 기반.

## 7. 모션 시스템

- 3단 다이얼(볼륨과 동일한 UX 패턴): **정적 / 은은 / 리치**.
  - 정적: 애니메이션 없음.
  - 은은: 스크롤 진입 페이드·슬라이드, hover 살짝. (기본값)
  - 리치: 패럴랙스, 카운트업, 스태거 등장, 스티키 스크롤, 캐러셀 자동재생.
- 프로젝트 전역(MVP). 페이지별 오버라이드는 고도화.
- 스타일 팩이 추천 기본값 제공, 사용자가 덮어씀.
- 항상 `prefers-reduced-motion` 존중.

## 8. 편집 단계 (빌더)

생성 후 빌더에서 수정. **디자인 층은 잠금, 콘텐츠·구조 층만 개방.**

| 층 | 편집 가능 |
|----|-----------|
| 콘텐츠 | 텍스트, 링크(href), 미디어 교체(이미지·영상·gif) |
| 구조 | 섹션 순서 재배치, 삭제, 추가. 팔레트 = **추천-우선**(타입 권장 섹션 강조 + "모든 섹션 보기"로 전체). 어차피 팩이 스타일 잠금 → 어떤 섹션도 온브랜드 |
| 디자인 | ❌ 잠금 (토큰·레이아웃은 팩이 강제) |

기존 드래그 빌더(`app/builder.html`)가 구조 편집의 기반. 여기에 인라인 콘텐츠 편집을 얹는다.

## 9. 출력 / 패키징

**원칙: PageDoc = 단일 진실원본(SSOT). 출력 포맷마다 독립 익스포터.** 새 포맷 추가 = 익스포터 하나 더, PageDoc·팩 구조는 불변.

### 출력 타깃 3개

| 타깃 | 익스포터 | 시기 | 비고 |
|------|---------|------|------|
| **미리보기 + 개발 핸드오프** | **깔끔 시맨틱 HTML + 토큰 CSS** | MVP | 보기용·개발용 겸용. 매직넘버 없이 CSS 변수. flexbox 기반 → Figma 변환 품질도↑ |
| **Figma 시안 (Tier 1)** | HTML→Figma 변환 (`html.to.design` 등 플러그인) | MVP~고도화 | 납작한 비주얼 레이어. 커스텀 개발 거의 0. 품질은 깔끔HTML이 받침. 레퍼런스·핸드오프용 |
| **Figma 네이티브 DS (Tier 2)** | PageDoc→Figma 컴포넌트·변수·오토레이아웃 (`cc-figma-*`, `figma-generate-*`) | 옵션·후속 | 진짜 편집형 DS 파일. 팩의 Figma 쌍둥이 필요(추가 저작). 큰 작업 |
| **프레임워크 코드 (React 등)** | 프레임워크 익스포터 | 옵션·후속 | 실제 제품 스택 확정 시 |

- **MVP는 깔끔 HTML/CSS 하나로 "보기 + 개발 + (변환)Figma"를 다 커버.** 렌더러가 처음부터 품질 코드를 뽑는 게 전제.

### 패키징 (HTML 출력)

| 프로젝트 종류 | 형태 |
|---------------|------|
| **단일**(랜딩·공지) | 완전 독립 **HTML 1파일** (CSS·JS 인라인). 어디든 배포 |
| **다중**(사이트) | **실개발식 폴더 + zip** |

```
site.zip
 ├ index.html  features.html  notice.html …
 └ assets/
     ├ pack.css     (= 스타일 팩 토큰, 공통)
     ├ motion.js    (= 모션 층, 공통)
     └ img/*
```

- 다중 페이지는 공통 `pack.css`·`motion.js`·네비를 공유하고 서로 `<a href>`로 연결(실제 사이트처럼).
- 스타일 팩이 프로젝트 레벨이라 공통 CSS 한 파일로 뽑기 자연스러움.

### AI 개입 사다리 (한정성 vs 통제·비용)

한 번에 "고정 팩 → AI가 다 그림"으로 뛰지 않는다. 아래로 갈수록 자유↑ / 통제·비용·리스크↑.

| Lv | AI가 하는 일 | 한정성 깸 | 리스크 | 비용 | 시기 |
|----|------------|---------|-------|------|------|
| **0** | 없음. 팩 고정, 조립만 | — | 없음 | 0 | MVP |
| **1** | 섹션 선택·카피·variant 선택 (값은 팩 스케일 내) | 조합 다양성↑ | 낮음 | 소액(텍스트) | 고도화 |
| **2** ⭐ | **새 토큰셋(팔레트·타이포·리듬) 생성** — 규칙 안에서. 구조는 재사용 | **크게 깸** | 중(대비·조화 검증규칙) | 소액 | 고도화+ |
| **3** | 새 레이아웃/구조를 코드로 생성 | 최대 | 큼(깨짐·품질통제) | 큼 | 프론티어·옵션 |
| **4** | 그래픽 생성 (SVG 벡터 = 안전판 / 래스터 이미지 = 프론티어) | 비주얼 자유 | 큼 | 큼 | 옵션·먼미래 |

핵심: 단조로움 깨는 가성비 지점 = **AI가 "새 레이아웃"이 아니라 "새 토큰 팩"을 생성(Lv2)**. 구조 재사용=품질 보증, 토큰 다양=비주얼 다양. 레이아웃 창작(Lv3)·래스터 생성(Lv4)은 최상위 툴도 조심하는 리스크 프론티어. MVP를 구조·토큰·콘텐츠로 깨끗이 분리하면 이 사다리가 자연히 얹힌다.

### 비용 모델

| 단계 | 무엇 | AI? | 운영비 |
|------|------|-----|--------|
| 레이아웃·스타일 | 팩 완비, 조립만 | ❌ | 0 |
| 콘텐츠 배치(MVP) | 대본 대화(정해진 질문) | ❌ | 0 |
| 그래픽(MVP) | 업로드 + 팩 키트 | ❌ | 0 |
| 정적 호스팅·저장 | 무료티어 + localStorage | ❌ | 0 |
| 섹션추론·카피(고도화) | 텍스트 LLM(싼 모델) | ✅ | 페이지당 소액, 예산 상한·캐싱으로 통제 |
| 토큰 생성(Lv2) | 텍스트 LLM | ✅ | 소액 |
| 이미지 생성(Lv4) | 이미지 모델 | ✅ | 큼·후순위 |

**MVP 운영비 사실상 0.** AI 비용은 고도화의 *텍스트*에만(소액·통제 가능), *이미지 생성*은 완전 별개·먼미래. "다 정리돼 있으면 진짜 무료" — 대가는 돈이 아니라 **사전 저작 노동**.

### NL 프론트도어 토큰 비용 (§3-bis)

| 항목 | 내용 | 비용 관리 |
|------|------|----------|
| **진입 판단 1콜** | 자연어+파일 요약 → 단/다·IA·섹션 JSON. **싼 모델(Haiku급)**. 입력 수 K, 출력 <1K 토큰 | 프로젝트당 **1회**. 사실상 센트 미만 |
| **카탈로그 컨텍스트** | 페이지타입·섹션 메뉴를 프롬프트에 동봉(선택지 제약용) | **프롬프트 캐싱** → 반복 호출 시 캐시 히트로 거의 무료 |
| **되물음(옵션)** | 정보 부족 시 좌측 대화 후속 질문 | 필요할 때만·짧은 텍스트. **예산 상한** 설정 |
| **파일 파싱** | 첨부 문서 텍스트 추출 | 클라이언트/서버리스에서 텍스트만 뽑아 전달(원문 통째로 X) |
| **섹션 variant 랜덤** | 표현형 선택 | **결정론적 로직 = AI 0** |
| **팩 저작 생성** | 팩 다수 생성 | **저작-타임** 비용(운영 아님). 우리가 만들 때만 씀 |

- 정리: **런타임 AI = 진입 판단 1콜(캐싱된 카탈로그) + 선택적 되물음**뿐. 나머지(조립·variant·렌더·출력)는 전부 결정론적 = 0.
- 통제 수단: 싼 모델 + 프롬프트 캐싱 + 프로젝트당 예산 상한 + NL은 편의층(없어도 대본으로 동작).

## 11. 앱 아키텍처 · 배포 · 저장

목표: **최종 전사 사용**, MVP는 **몇몇 구성원**. 제약: **개발 리소스 못 쓸 확률 큼** → 무백엔드 정적으로 간다(앱 자체는 지금 우리가 만드는 정적 SPA라 개발팀 불필요).

| 항목 | MVP | 전사 확장(후속) |
|------|-----|----------------|
| **앱 형태** | 정적 SPA (빌드리스, 브라우저서 조립) | 동일 + 얇은 서버리스 |
| **배포** | **Vercel** 무료티어 → 공유 URL 하나. 몇몇이 링크로 접속 | 동일. 서버리스 함수(AI·인증) 얹기 |
| **저장** | **localStorage(자동) + JSON 내보내기/불러오기** | BaaS(Supabase 등) 클라우드 저장 |
| **공유** | **파일(JSON) 주고받기** (내보내기→슬랙/드라이브→불러오기) | 같은 URL서 실시간 공유(BaaS) |
| **AI** | 없음 | 서버리스 함수로 Claude API(키 숨김) |
| **인증** | 없음 | 필요 시 추가 |

- MVP는 백엔드·계정·DB 0. 운영비 0(§10 비용 모델).
- 실시간 공유·AI·클라우드 저장을 원하는 순간에만 *관리형 서비스*(BaaS·서버리스) 살짝 붙임 — 풀 개발팀 아님.

## 12. 값 입력 UX (MVP = 대본형 대화, AI 아님)

대화창이 컨테이너, 그 안에 슬롯 타입별 인라인 폼 위젯. **정해진 질문에 답 채우는 "대화형 폼"** (Claude 프로젝트 시작 느낌). 이해·추론 0 = 무료.

**프리뷰 모델 = B: 섹션별 미니 프리뷰.** 슬롯 채우면 그 섹션이 인라인으로 즉시 렌더 → AX 느낌. 전체 조립 프리뷰·구조편집은 생성 후 빌더로 분리(입력→생성→빌더 구조 유지).

### 입력 흐름

```
① 프로젝트 종류 → ② 페이지 타입 → ③ 볼륨(섹션 수)
   → ④ 스타일 팩 + 모션   (콘텐츠 前 — 프리뷰가 실제 스타일로 나오게)
   → ⑤ 섹션별 값 입력 (채우면 그 섹션 인라인 렌더)
   → 생성 → 빌더
```
- ①~④ = 시작 선택(칩·카드). ⑤ = 섹션 하나씩 폼카드 + 미니 프리뷰.
- **스타일 팩은 입력 중 언제든 교체 → 프리뷰 즉시 리스킨**(팩=CSS만). 강력한 데모 순간.

### 슬롯 타입별 위젯

| 슬롯 타입 | 위젯 |
|---|---|
| text | 텍스트 필드 / 여러 줄 |
| link | URL 필드 |
| media | 업로드 드롭존 / URL |
| list(반복) | 항목 행 추가 (min/max 가드) |
| choice(종류·팩·볼륨·모션) | 칩 / 카드 선택 |

- 슬롯마다 **예시 플레이스홀더** ("제품 한 줄 — 예: '팀을 위한 협업 캘린더'") → 대본이어도 친절, 비어도 프리뷰 안 깨짐.

### 입력 정보 = 공유 사실 + 섹션별 값

- **공유 사실 (프로젝트에서 한 번 입력 → 모든 페이지·섹션 자동 주입):** 제품명·로고·태그라인·주CTA·문의링크. 반복 입력·오타·페이지간 불일치 방지. 다중 페이지일수록 이득.
- **섹션별 값 (그때그때 입력):** 이 기능 설명, 이 후기, 이 요금제 등 섹션 고유 내용.

**받는 정보 어휘 (제품소개 사이트):** 정체성(제품명·로고·태그라인·카테고리) · 가치(문제·가치제안·타깃) · 기능[] · 작동방식[] · 신뢰근거(지표·로고·후기·사례) · 미디어[] · 요금제[] · 소식[] · CTA/문의 · 회사. 섹션들이 여기서 값을 끌어옴 (Hero.title←태그라인, Feature←기능[], Pricing←요금제[]).

- 고도화: 이 대본 자리를 AI가 대신 채움(자유 서술 이해 → 슬롯 매핑). 위젯·프리뷰 구조 그대로.

## 13. 페이지 타입 카탈로그 (MVP, 잠정)

**MVP = 온사이트 제품사이트 실구축** → 사이트의 페이지 타입을 다 커버해야 함. 온사이트 사이트맵이 카탈로그를 정한다(기획 진행 중 → **잠정**, 확정 시 조정).

### 시퀀싱

1. **1차: 메인 + 도입문의 손디자인** (지금 기획 중) → **DS 1차 추출 = 온사이트 팩 씨앗**
2. 그 팩으로 **나머지 페이지 생성**
3. 팩·섹션 빈 곳 채우며 카탈로그 완성

### 잠정 카탈로그

| 페이지 타입 | 단/다 | 비고 |
|---|---|---|
| 메인홈 | 사이트 | 1차 손디자인 |
| 도입문의 | 사이트 | 1차 손디자인 (폼) |
| 제품 기능소개 | 사이트 | |
| 이벤트/뉴스룸 | 사이트 | |
| 업데이트노트 | 사이트 | 체인지로그/릴리즈 섹션 |
| 매뉴얼 | 사이트 | breadcrumb·toc·스텝·spec table |
| 요금 비교 | 사이트 | pricing·comparison |
| 랜딩(행사·프로모션) | 단일 | 사이트와 별개, 필요 시 생성 |

### 노동 현실

- 페이지 7~8개지만 **섹션 합집합의 ~80%가 이미 `registry.js`에 있음** (hero·feature·imgtext·process·card·blog·stat·price·comparison·form·cta·footer …).
- **템플릿 = 싼 설정**(섹션 리스트+티어). 진짜 일 = **섹션 빈 곳 채우기**(매뉴얼 toc/breadcrumb, 업데이트노트 changelog, 요금 상세) + **온사이트 팩**(한 번).
- 기존 `TEMPLATE_STRUCTURE.md`에 productIntro(16섹션)·manual 템플릿 초안 있음.
